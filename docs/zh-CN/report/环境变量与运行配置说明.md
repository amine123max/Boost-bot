# 环境变量与运行配置说明

## Boost 智能体运行时

内置运行时源码位于 `bot/`，运行 `node scripts/prepare-boost-bot.mjs` 准备运行目录。`BOOST_BOT_ROOT` 可指定运行目录，`BOOST_BOT_NODE` 可指定 Node 可执行文件；`BOOST_BOT_CATALOG_URL` 与 `BOOST_BOT_CATALOG_PUBKEY` 需要同时配置，才能启用额外的签名目录。默认使用随应用打包的智能体。外观偏好保存在设备本地的 `boost.bot.appearance.v1`。运行权限与打包说明见 [Boost Bot](../../../bot/README.md)。

## 目标

本文档用于集中说明 Boost 的环境变量加载规则、设置页持久化规则，以及常用配置项的推荐改法。

源码中的 `BOOST_*` 常量仍是最终准入标准；本文档负责给协作者提供稳定入口，不替代源码校验。

## 多节点上游代理

sing-box 采用本地优先策略：先检查已托管内核、Boost 程序目录、服务进程的 PATH、正在运行的 sing-box / v2rayN 等程序目录，以及常见安装位置。仅在版本为 1.12+ 且包含 Clash API、uTLS 时使用。找到可用内核即可直接复用，无需先联网检查更新；「安装内核」也会再次扫描本地，仍未找到时才从官方下载。内核管理显示实际路径和版本，并提供「扫描本地」重新发现入口。扫描只查询程序路径和版本，不读取其他软件的节点配置，也不会覆盖其程序文件。只有明确执行更新、检查更新，或开启每日自动更新后才检查线上版本。

代理管理已从设置页移到「测试 → 网速测试」（`/tests/network/`），页签沿用原有按钮样式。右上角「导入节点」支持粘贴链接、文本文件和「添加本地代理」，最多 32 个节点。节点卡片按参考样式显示名称、国旗、绿色延迟标签、圆形测速按钮和右对齐的测试时间；测速详情默认收起。双击卡片或聚焦后按 Enter / 空格固定节点，单击卡片不改变策略，测速和删除按钮不会触发选择。首页可通过 `/home` 或 `/home/` 直接访问并刷新，`/` 保留兼容入口。

导入支持 HTTP、HTTPS、SOCKS5、Trojan 和 AnyTLS，也支持 `7897`、`127.0.0.1:7897`、`localhost:7897`、`[::1]:7897` 等本地端口简写（默认 HTTP / 混合端口）；SOCKS5 可通过添加本地代理对话框选择，或使用 `socks5://127.0.0.1:1080`。这里的本地是 **Boost 服务运行的机器**，不是访问 Web 控制台的浏览器所在机器。本地节点导入后自动通过该代理向 `https://ipwho.is/` 查询出口国家；成功后显示实测国旗，失败时显示待检测并限频重试，不根据本地地址猜测国家。其他节点可先展示名称中的地区信息，完成测速后以真实出口查询结果更新。

既有单个 HTTP / HTTPS / SOCKS5 配置继续使用，不依赖额外内核。节点列表仍保存在 `gateway.upstream_proxy_url`，`BOOST_UPSTREAM_PROXY_URL` 支持换行分隔；未配置时才使用旧的 `BOOST_PROXY_LIST` 账号固定分配模式。选择策略、手动节点、账号绑定、自动更新开关及托管内核路径保存在 `gateway.proxy_control.v1`，默认「稳定优先」、无账号绑定、自动更新关闭。稳定节点 ID 不受名称和列表排序影响；凭据或服务器变更视为不同节点。

多节点自动选择或 Trojan / AnyTLS 需要 sing-box 1.12+（含 Clash API、uTLS）。可以在测试面板的「内核管理」中手动安装、检查更新、更新，或启用每日自动更新。默认不自动下载。安装器从 sing-box 官方 GitHub 稳定发布下载当前平台内核，核对官方 SHA-256、实际版本、编译能力和节点配置后才切换；下载与验证失败时保留当前内核。托管文件位于数据库目录的 `proxy-core/`，完成升级后移除旧的托管文件和下载包，不创建备份。启动前没有可用代理内核时，允许连接官方 GitHub 以完成内核安装；AI 请求仍阻断。系统需要 `tar` 解包工具（Windows 自带的 `tar.exe` 可用）。也可以继续将外部 `sing-box.exe` / `sing-box` 放在 Boost 可执行文件同目录或服务进程的 `PATH` 中。更新器不会覆盖其他软件的内核。

示例（请替换服务器、密码及 SNI）：

```text
trojan://password@jp1.example.com:443?security=tls&sni=jp1.example.com&fp=chrome&type=tcp#日本-1
anytls://password@jp2.example.com:443?security=tls&sni=jp2.example.com&fp=chrome&type=tcp#日本-2
```

原生节点目前支持 TCP + TLS、`sni`、`fp`、`alpn`、`insecure` / `allowInsecure` 参数，密码需按 URL 规则编码。不支持的协议和传输参数会明确报错。默认校验 TLS 证书；只有链接明确设置 `insecure=1` / `allowInsecure=1`（或 `true`）时才关闭校验。

内核仅监听随机的 `127.0.0.1` 端口，代理入口和控制接口均需要随机凭证，配置通过标准输入传递。核心未就绪时也可以导入并保存合法节点，面板显示安装提示，流量保持阻断。启动错误、内核不可用或全部节点故障均不新增直连出口。服务关闭时停止内核，意外退出时尝试重启。

自动策略使用 `https://www.gstatic.com/generate_204` 每分钟检测连通性。「稳定优先」使用 200 ms 切换容差，「低延迟优先」使用 1 ms 容差，「手动固定」始终使用指定节点。手动测速每节点进行 3 次 HTTP 连通性检测、下载最多 1 MB Cloudflare 测试数据并查询出口地区；失败比例来自这 3 次请求，代表连通性失败率，并非 ICMP 丢包测量。卡片详情展示下载速度、抖动和失败比例；缺少实测值显示破折号。面板每 3 秒同步状态，测速并发限制为 3 个，可停止后续检测。

账号列表、账号测试卡片和编辑账号弹窗均提供节点选择器。默认跟随全局策略，绑定后通过独立认证入口固定路由；网关 HTTP / SSE / WebSocket、Token 刷新、用量/订阅查询、账号预热均遵循绑定。删除绑定节点后，绑定关系继续保留并阻断该账号请求，直到重新指定或恢复跟随全局。绑定不允许访问不存在的账号或节点，仅管理员可管理网络与内核。自动策略变更不主动中断已有连接；重新导入配置或更新内核会重建代理入口，进行中的连接可能需要重试。

请只填写符合预期地区的节点：自动选优不验证地理位置，切换节点可能更换公网 IP，节点运营商本身也可能更换出口。需要完全固定 IP 时应使用单个有固定出口的代理；多个节点不能保证同一公网 IP。已有连接会继续使用原出口直到连接结束。

## 配置来源与优先级

当前配置来源主要有四层：

1. 系统环境变量 / 启动命令环境变量
2. 可执行文件同目录环境文件：`boost.env` -> `Boost.env` -> `.env`
3. `app_settings` 持久化表
4. 桌面端设置页的专属设置卡片 / 高级环境变量编辑器

实际生效优先级可概括为：

- 当前进程已存在环境变量（包括启动前系统环境变量，以及启动时从 `env` 文件读入的值）
- 专属设置卡片 / 持久化 `envOverrides`
- 代码默认值

补充规则：

- 环境文件只会注入“当前进程尚未定义”的变量
- 进程启动后，设置页保存的 `envOverrides` 只会补齐“当前进程还没有”的变量
- 桌面端当前已改为 `env` 优先：如果进程里已经有同名 `BOOST_*` 变量，设置页持久化配置不会再覆盖它
- 支持热更新的 service 运行时配置会立即 reload，但同名 `env` 已存在时会优先沿用 `env`
- bootstrap 级变量仍要求在进程启动前准备好

## env 文件放哪

当前进程会按下面顺序在“可执行文件同目录”查找环境文件：

- `boost.env`
- `Boost.env`
- `.env`

也就是说：

- 启动桌面端程序时，`env` 文件要放在桌面端实际可执行文件所在目录
- 启动 `boost-start` / `boost-service` / `boost-web` 时，`env` 文件也要放在对应可执行文件旁边
- 三种文件名只会命中一个，优先推荐统一使用 `boost.env`

## 常用变量分组

### 地址与入口

- `BOOST_SERVICE_ADDR`：service 地址，默认 `localhost:48760`
- `BOOST_WEB_ADDR`：web 地址，默认 `localhost:12580`
- `BOOST_WEB_ROOT`：web 静态资源目录
- `BOOST_LOGIN_ADDR`：本地 OAuth 回调监听地址

### 网关与上游

- `BOOST_UPSTREAM_BASE_URL`
- `BOOST_UPSTREAM_PROXY_URL`
- `BOOST_UPSTREAM_TOTAL_TIMEOUT_MS`：网关请求总超时，单位毫秒；默认 `0`，表示服务端不主动按总时长截断请求。
- `BOOST_UPSTREAM_STREAM_TIMEOUT_MS`
- `BOOST_USE_WEBSOCKET_UPSTREAM`：是否让 ChatGPT `/v1/responses` 流式上游优先尝试 WebSocket 传输；默认 `0`。这是实验开关，失败会回退 HTTP 流式路径，会沿用上游代理与连接超时配置。
- `BOOST_SSE_KEEPALIVE_INTERVAL_MS`
- `BOOST_PROXY_LIST`
- `BOOST_ROUTE_STRATEGY`

### Codex 图片生成

- `BOOST_CODEX_IMAGE_GENERATION_ENABLED`：是否启用图片生成兼容链路，默认 `1`。
- `BOOST_CODEX_IMAGE_GENERATION_AUTO_INJECT_TOOL`：普通 `/v1/responses` 请求是否自动注入 `image_generation` tool，默认 `1`，与 Codex 官方客户端行为保持一致。显式由客户端传入 tool 时不重复注入。
- `BOOST_CODEX_IMAGE_MAIN_MODEL`：Images API 兼容入口内部使用的主对话模型，默认 `gpt-5.4-mini`。
- `BOOST_CODEX_IMAGE_TOOL_MODEL`：图片工具模型，默认 `gpt-image-2`。

补充说明：

- `/v1/images/generations` 与 `/v1/images/edits` 会转换为内部 `/v1/responses + image_generation tool` 链路。
- Codex CLI 原生传入 `tools[].type = "image_generation"` 时会保持透传，不会影响既有文本请求链路。

## 文件夹示例

### 桌面端

Windows 桌面端最直观的放法如下：

```text
Boost/
├─ Boost.exe
├─ boost.env
└─ 其他运行库文件...
```

对应 `boost.env` 示例：

```dotenv
BOOST_SERVICE_ADDR=localhost:48760
BOOST_UPSTREAM_PROXY_URL=http://127.0.0.1:7890
BOOST_UPSTREAM_TOTAL_TIMEOUT_MS=0
BOOST_UPSTREAM_STREAM_TIMEOUT_MS=600000
BOOST_SSE_KEEPALIVE_INTERVAL_MS=15000
```

补充说明：

- 桌面端会读取程序同目录下的 `boost.env`
- 但桌面端默认数据库不放在程序目录，而是放在系统应用数据目录
- 默认数据库位置可参考根说明里的“默认数据目录”： [../README.md](../README.md)

### Service 版

如果你用的是 `boost-start` 一键启动包，更推荐把程序和 `env` 文件放成下面这样：

```text
boost-service-bundle/
├─ boost-start.exe
├─ boost-service.exe
├─ boost-web.exe
├─ boost.env
└─ web/
   └─ ...
```

对应 `boost.env` 示例：

```dotenv
BOOST_SERVICE_ADDR=0.0.0.0:48760
BOOST_WEB_ADDR=0.0.0.0:12580
BOOST_DB_PATH=./data/codexmanager.db
BOOST_RPC_TOKEN_FILE=./data/codexmanager.rpc-token
BOOST_UPSTREAM_PROXY_URL=http://127.0.0.1:7890
```

这时目录通常会长成这样：

```text
boost-service-bundle/
├─ boost-start.exe
├─ boost-service.exe
├─ boost-web.exe
├─ boost.env
├─ data/
│  ├─ codexmanager.db
│  └─ codexmanager.rpc-token
└─ web/
   └─ ...
```

补充说明：

- `BOOST_DB_PATH=./data/codexmanager.db` 这种相对路径，会按“可执行文件所在目录”解析
- `BOOST_RPC_TOKEN_FILE` 也是同样规则
- 如果你不写 `BOOST_DB_PATH`，Service 版默认会把数据库放到程序目录下的 `codexmanager.db`

## 排障建议

### OpenAI 上游代理到底作用在哪

`BOOST_UPSTREAM_PROXY_URL` / 设置页“OpenAI 上游代理”当前主要接管的是：

- 网关向上游平台发起的请求
- 启用 `BOOST_USE_WEBSOCKET_UPSTREAM=1` 后的 ChatGPT 上游 WebSocket 请求
- 用量查询请求
- `refresh_token` 刷新 access token 的请求

安全提示：

- `auth.openai.com` / `oauth/token` 等登录态刷新链路必须走 OpenAI 支持的地区出口；不要把香港等受限节点纳入这条链路的自动轮换。
- 如果刷新请求返回 `unsupported_country_region_territory`，Service 会将账号标记为 `refresh_token_region_blocked` 并暂停后续自动刷新；修正代理后需要手动恢复账号。

默认不接管的是：

- 你本机浏览器 / 桌面端访问 `localhost` / `127.0.0.1` 的本地回环请求
- 本地 service 与 web 之间的回环通信
- 登录回调成功后的 OAuth `code -> token` 兑换链路

补充规则：

- 如果同时设置了 `BOOST_UPSTREAM_PROXY_URL` 和 `BOOST_PROXY_LIST`，上游代理地址配置优先，旧的按账号分配代理池会被旁路。
- `BOOST_PROXY_LIST` 适合按账号稳定分配多个出口；`BOOST_UPSTREAM_PROXY_URL` 支持一个代理或换行分隔的自动择优节点列表。

### 改了 env 文件但没生效

优先检查：

1. 是否重启了对应进程
2. 是否已有同名系统环境变量
3. 是否又被设置页持久化配置覆盖

### 设置页改了但服务行为没变

优先检查：

1. 该配置是否属于“重启后生效”
2. 当前改的是专属设置卡片还是通用环境变量编辑器
3. service 日志里是否出现 reload / apply 失败

### 设置了网关传输参数但长流还是异常

优先检查：

1. `BOOST_UPSTREAM_STREAM_TIMEOUT_MS` 是否过短，导致长时流式请求提前超时
2. `BOOST_UPSTREAM_TOTAL_TIMEOUT_MS` 是否被设置成了非 `0` 的较短值，导致服务端按总时长截断
3. `BOOST_SSE_KEEPALIVE_INTERVAL_MS` 是否过长，导致中间链路把 SSE 误判为空闲断开
4. 客户端本身是否还有自己的超时或代理空闲断开限制；请求日志里的 `120s/1.8s` 左侧是请求总耗时，右侧是首包耗时，不一定代表服务端总超时配置

### 高并发下 SQLite FD 过高

优先检查：

1. `BOOST_STORAGE_MAX_CONNECTIONS` 是否被调得过大；默认 `32` 会对同一数据库路径施加总连接上限
2. `BOOST_FRONT_PROXY_MAX_BLOCKING_THREADS` 是否高于存储连接上限；默认会跟随存储连接池上限并限制在 `32` 以内
3. `BOOST_STORAGE_ACQUIRE_TIMEOUT_MS` 是否过短；连接池耗尽时，请求会等待空闲连接，超时后返回存储不可用错误
4. Linux Service 版仍建议设置合理的 `ulimit -n`，但不应再依赖无限增大 ulimit 来兜住 SQLite 连接峰值

### 本地回环请求异常

优先检查：

- 是否把系统代理错误地应用到了 `localhost/127.0.0.1`
- 地址是否被写成非预期大小写或非 loopback 主机名
